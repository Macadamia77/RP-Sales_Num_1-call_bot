01

목표와 첫 버전의 범위

무엇을 자동화하고, 어느 지점에서 성공으로 판단할지 먼저 정합니다.

이 시스템의 목표는 지정한 건물의 관리사무소 업무용 연락처를 통화로 확인하고, 출처와 대화 근거를 함께 저장하는 것입니다. 사용자는 목소리를 한 번 등록하고, 건물 정보와 발신 대상 목록, 대화 템플릿을 설정합니다. 서버는 전화를 한 건씩 실행하고 결과를 모읍니다.

MVP · 우선 구현

처음부터 필요한 기능

  • 본인 음성 등록 및 미리 듣기
  • 건물명·주소·수신번호·문의 목적 입력
  • 템플릿 편집 및 텍스트 대화 테스트
  • 동시 통화 1개, 발신·중단·종료 제어
  • 번호 추출·상대방 재확인·대화록 저장
  • 결과 조회, 근거 확인, CSV 다운로드
NEXT · 검증 후 확장

후속 단계에 붙일 기능

  • 여러 통화 동시 실행과 예약 발신
  • 통화 중 사람에게 넘기기
  • ARS 메뉴와 키패드 입력 처리
  • 소개받은 번호의 후속 발신
  • 수집한 번호로 관리사무소 연결 검증
  • 여러 목소리·조직·권한 관리
첫 버전의 성공 조건“관리사무소 번호라고 안내받았고, 읽어 준 전체 번호가 맞다는 답을 받았다”까지를 성공으로 정의합니다. 그 번호로 실제 관리사무소에 연결되는지는 별도 검증 상태로 남깁니다.

이 문서는 구현 설계와 예시를 제공합니다. 전화가 연결되는 실행 앱이나 API 연동이 완료된 제품은 아니며, 예시 코드는 운영 코드로 사용하기 전에 선택한 공급사의 규격에 맞춰 구현해야 합니다.

별도 저장 경로: 통화 이벤트 + 화자별 대화록 + 번호 후보 + 확인 근거 → 데이터베이스

첫 버전은 STT → LLM → TTS를 연결하는 구조를 권장합니다. 중간 텍스트를 확인할 수 있어 번호 정규화, 고정 문구 적용, 대화 검토가 편합니다. OpenAI 문서도 각 단계를 직접 제어하거나 교체하려는 경우 이 방식을 제시합니다.[1]

코드가 결정할 일

전화 걸기와 끊기, 발신 허용 목록, 통화 시간 제한, 숫자 낭독 문장 생성, 데이터 형식 검증, 확인 근거가 없는 성공 상태 차단.

음성을 직접 주고받는 Realtime API도 대안입니다. 별도 STT·TTS 연결을 줄일 수 있지만, 원하는 목소리의 사용 권한과 텍스트 제어 수준을 확인해야 합니다. 이 설명서는 각 단계를 분리하는 구조를 기준으로 합니다.[1]

03

목소리·전화 연결 준비

목소리 생성 권한과 국내 통화 가능 여부를 별도로 확인합니다.

목소리는 한 번 등록하고, 통화마다 새 문장을 합성합니다.

  1. 본인 음성을 녹음합니다.

    조용한 환경에서 평소 전화할 때의 말투로 녹음합니다. 음악, 다른 사람의 목소리, 과한 잡음을 피하고 사용하는 서비스의 동의 절차를 진행합니다.

  2. 음성 합성 서비스에 등록합니다.

    등록 API에서 받은 voice_id를 저장합니다. 이후에는 문장과 이 ID를 전송해 같은 목소리로 음성을 생성합니다.

  3. 한국어 문장과 숫자를 미리 들어 봅니다.

    건물명, 주소, 전화번호, 짧은 감사 인사를 재생합니다. 원본 파일의 음질뿐 아니라 실제 전화망을 통과한 음질을 확인합니다.

목소리 옵션공식 문서 기준설계에 반영할 점
ElevenLabs IVC깨끗한 단일 화자 녹음 약 1~2분 권장. 등록한 목소리를 음성 합성에 사용하며 한국어 지원 모델이 있습니다.[5][6]한국어 전화 음질과 숫자 발음 평가 후 모델 선택
OpenAI Custom voices이용 자격이 있는 고객에 한정됩니다. 동의 녹음과 일치하는 음성 샘플이 필요합니다.[7]계정에서 기능 사용 가능 여부를 먼저 확인

상대에게 표시되는 발신번호는 별도 설정입니다.

목소리를 내 목소리로 만드는 것과 내 전화번호가 발신번호로 표시되는 것은 서로 다른 기능입니다. 전화 사업자 계정, 번호 소유 확인, 국내 발신 경로가 필요합니다. 예를 들어 Twilio의 발신번호는 계정이 소유한 Twilio 번호 또는 검증된 번호여야 합니다.[2]

국내 연동에서 먼저 검증할 항목Twilio의 한국 가이드에는 국내 발신번호 표시가 보장되지 않는 것으로 안내됩니다. “한국 번호에 전화가 연결된다”와 “원하는 010·02 번호가 표시된다”는 별도로 검증해야 합니다. 한국 번호 공급·재고·계정별 사용 가능 여부도 공급사에서 확인합니다.[4]

발신 API로 통화를 시작하고 상대가 받으면 양방향 음성 스트림을 서버에 연결합니다. Twilio의 경우 <Connect><Stream> 방식으로 구현할 수 있습니다. 음성 형식도 맞춰야 하며, Twilio로 보내는 스트림은 헤더 없는 8kHz μ-law 음성을 base64로 인코딩하는 규격입니다. 다른 공급사를 사용하면 해당 규격으로 변환합니다.[3][8]

공급사 선정 순서: 국내 통화 조건 확인 → 본인 테스트 번호에 연결 → 양방향 음성 송수신 → 실제 발신번호 확인 → 음성 에이전트 결합.

04

통화와 예외 처리

진행 단계는 명확하게, 질문은 짧게, 상대가 말하면 먼저 듣습니다.

인사→건물 확인→번호 요청→후보 수집→번호 재확인→저장·종료
AI

안녕하세요. 요청자님의 부탁으로 연락드린 AI 전화 도우미입니다. 예시빌딩 관리사무소 전화번호를 여쭤봐도 될까요?대리 통화임을 알리고 목적을 설명합니다.

어느 예시빌딩이요?

AI

입력해 주신 주소에 있는 예시빌딩 말씀드립니다.실제 구현에서는 입력된 정확한 주소를 사용합니다.

상대

네, 맞아요.

AI

안내해 주셔서 감사합니다. 좋은 하루 보내세요.상대방 재확인 완료로 기록합니다. 실제 연결 검증은 미실시 상태입니다.

상황권장 응답·처리저장 결과
번호를 못 들음“국번 다음 네 자리만 다시 말씀해 주시겠어요?”처럼 필요한 부분만 다시 질문후보 유지, 확인 대기
건물이 다름주소와 건물명을 한 번 더 확인. 불일치하면 종료잘못된 문의처
모른다고 함확인할 다른 문의처를 아는지 한 번 질문 후 종료미확보 또는 소개 번호
다른 번호 소개번호의 대상과 용도를 확인하고 후보로 저장관리사무소 번호와 구분
나중에 전화 요청요청 시간·사유를 저장하고 설정된 정책에 따라 처리재통화 요청
거절·종료 요청짧은 감사 인사 후 종료하고 해당 작업의 재시도 대상에서 제외거절, 재발신 제외
부재·사서함·ARS첫 버전에서는 분류 후 종료. 불확실하면 검토 필요로 표시부재 / 자동응답 / 불명
긴 침묵짧게 한 번 확인한 뒤 설정된 대기 제한을 넘으면 종료응답 없음

말 끊기를 처리하는 세 가지 동작

상대가 말하기 시작하면 생성 중인 답변 취소 → 전화 재생 버퍼 비우기 → 새로운 발화 처리를 함께 실행합니다. 취소 전에 생성된 늦은 음성 조각이 뒤늦게 재생되지 않도록 각 응답에 ID를 붙이고, 현재 응답 ID와 다른 조각은 버립니다. Twilio는 재생 버퍼를 비우는 clear 메시지를 제공합니다.[8]

서버에는 “생성된 답변”과 “실제로 송출된 답변”을 구분해 기록합니다. 중간에 끊긴 문장을 상대방이 끝까지 들었다고 가정하지 않습니다.

05

대화 템플릿 설계

정해진 대사는 그대로, 후속 질문은 맥락에 맞게 생성합니다.

템플릿은 입력 변수, 고정 문구, 상황별 응답 규칙, 완료 조건으로 나눕니다. 고정 인사와 번호 재확인 문구는 코드가 작성하고, LLM은 설명과 후속 질문을 생성하도록 하면 제어하기 쉽습니다.

템플릿과 함께 현재 단계, 대화 이력, 번호 후보를 LLM에 전달합니다. 상대방 발언은 대화 데이터로 취급하고 시스템 명령으로 실행하지 않습니다. “다른 번호에 전화해”라는 발언은 소개 내용으로 기록하며, 발신은 서버가 관리하는 작업 목록과 정책을 따릅니다.

인사 문구, 문의 목적, 설명 방식, 말투, 모를 때의 후속 질문, 감사 인사. 저장 시 버전을 새로 만들고 통화마다 사용한 버전을 기록합니다.

시스템이 고정하는 영역

허위 신분·관계 생성 금지, 번호 추측 금지, 확인 근거 검증, 종료 요청 처리, 발신 범위·시간·횟수 제한, 외부 도구 실행 권한.

본인 목소리 사용 여부와 별개로 AI 대리 통화임을 알리는 인사를 넣습니다. OpenAI TTS 문서는 AI로 생성된 음성이라는 사실을 명확히 알리도록 요구합니다. 통화 기록을 남길 경우에는 실제 운영 방식에 맞는 안내를 인사 흐름에 추가합니다.[9]

06

전화번호 추출과 검증

통화 중 확인하고, 숫자와 근거를 함께 보존합니다.

  1. 확정된 상대방 발화에서 후보를 찾습니다.

    실시간 STT 중간 자막은 바뀔 수 있습니다. 확정 발화와 발화 ID를 기준으로 후보를 생성하고, 봇이 스스로 읽은 숫자를 신규 증거로 사용하지 않습니다.

  2. 원문과 정규화한 숫자를 분리합니다.

    예: “공이 일이삼사 오육칠팔” → 문자열 “02-1234-5678”. 앞자리 0을 보존하고, 지역번호나 누락된 자리를 임의로 채우지 않습니다.

  3. 번호의 대상과 형식을 확인합니다.

    관리사무소·부동산·다른 문의처·용도 불명을 구분합니다. 형식 검사는 오타를 찾는 보조 수단이며, 실제 사용 중인 번호라는 증거는 아닙니다.

  4. 코드가 만든 문장으로 다시 읽습니다.

    저장한 숫자에서 “공 이 / 일 이 삼 사 / 오 육 칠 팔”을 생성합니다. LLM이 숫자를 다시 생성하도록 하지 않습니다.

  5. 상대의 확인 또는 정정을 반영합니다.

    “네, 맞아요”가 방금 읽은 번호를 확인한 답인지 판단합니다. 숫자를 정정하면 이전 확인을 무효화하고 새 후보를 다시 읽습니다.

  6. 결과와 근거를 저장합니다.

    최종 번호, 번호를 알려준 발화, 봇이 읽은 내용, 상대의 확인 발화를 연결합니다. 확인 중 통화가 끊겼다면 후보 상태로 남깁니다.

번호 낭독은 별도 함수로 구현한국어 숫자 표기와 발음은 음성 모델마다 다를 수 있습니다. ElevenLabs 문서도 일부 모델에서 전화번호 정규화가 기대와 달라질 수 있음을 설명합니다. 저장용 숫자와 읽기용 문장을 분리하고 실제 전화에서 확인합니다.[6]
1후보 번호

번호를 들었지만 전체 숫자나 연락처의 용도가 아직 확인되지 않았습니다.

2상대방 재확인 완료

전체 번호를 다시 읽었고 상대가 맞다고 답했습니다. MVP의 성공 기준입니다.

3실제 연결 검증 완료

해당 번호에 연결해 대상 관리사무소임을 별도로 확인했습니다. 후속 기능입니다.

“아마 그 번호일 거예요”처럼 상대가 확신하지 않는 경우에는 추정 정보를 그대로 남깁니다. LLM이 자체적으로 매긴 신뢰도 점수만으로 성공 처리하지 않고, 실제 대화 근거와 재확인 여부를 기준으로 합니다.

08

개발 구성과 API 예시

웹 화면과 통화 처리를 분리하고, 전화 이벤트가 중복돼도 한 번만 실행되게 만듭니다.

FRONTEND

관리 웹 화면

목소리 등록, 대상 목록 입력, 템플릿 편집, 통화 상태 표시, 결과 검토. API 비밀키는 브라우저에 두지 않습니다.

BACKEND

API + 통화 워커

예: Python 또는 Node.js 서버. 발신 요청과 장시간 유지되는 음성 연결을 처리하고 통화 상태를 관리합니다.

STORAGE

DB + 파일 저장소

예: 관계형 DB에 작업과 결과 저장. 선택적 녹음은 파일 저장소에 두고 접근 권한과 삭제 시점을 관리합니다.

LLM 응답 설계 예시 · JSON
{
  "intent": "provided_contact",
  "next_action": "request_number_readback",
  "say_text": null,
  "contact_candidate": {
    "raw_text": "공이 일이삼사 오육칠팔",
    "digits": "0212345678",
    "role": "management_office"
  },
  "evidence_utterance_ids": ["u_06"]
}

이 예시는 LLM이 번호 재확인을 요청한 상황입니다. 서버는 후보와 원문을 검증한 뒤 숫자에서 읽기 문장을 만듭니다. next_action은 허용된 목록에서만 선택하도록 제한하고, 임의의 전화번호 발신이나 외부 작업을 모델 응답만으로 실행하지 않습니다.

중복 이벤트와 연결 끊김은 처음부터 고려같은 발신 요청이나 공급사 이벤트가 다시 도착해도 통화가 두 번 시작되거나 결과가 중복 저장되지 않게 합니다. 공급사 통화 ID, 이벤트 ID, 작업 잠금, 결과 저장의 고유 키를 사용합니다. 음성 연결이 끊긴 상태에서는 성공으로 처리하지 않습니다.
09

단계별 개발 순서

전화망의 가능성을 먼저 확인한 뒤, 대화 품질과 자동화를 단계적으로 결합합니다.

MILESTONE01

전화 연결 가능성 확인

공급사 계정과 발신번호를 준비하고 본인 테스트 번호로 한 통 발신합니다. 한국 연결, 표시 번호, 수신·송신 음성을 확인합니다.

완료 기준 · 실제 전화가 연결되고 양방향으로 소리가 들린다.
MILESTONE02

텍스트로 대화 로직 검증

전화 없이 가상의 상대 발화를 입력합니다. 번호 제공, 정정, 거절, 다른 건물, 다른 문의처를 테스트하고 상태 전이를 점검합니다.

완료 기준 · 확인 근거 없이 성공 처리하지 않고, 예외 상황에서 정해진 단계로 이동한다.
MILESTONE03

마이크로 음성 대화 구현

STT·LLM·본인 목소리 TTS를 연결합니다. 짧은 대화, 숫자 낭독, 말 끊기, 긴 침묵을 확인합니다.

완료 기준 · 생성 문장이 들리고, 상대 발화 시 재생을 중단하며, 끊긴 답변이 다시 나오지 않는다.
MILESTONE04

실제 통화 한 건을 끝까지 연결

전화 API에 음성 루프를 붙이고 대화록·후보 번호·재확인 결과를 DB에 저장합니다. 본인 또는 테스트 참여자와 검증합니다.

완료 기준 · 통화 시작부터 종료·결과 조회까지 한 흐름으로 완료된다.
MILESTONE05

관리 화면과 소규모 운영

완료 기준 · 번호와 대화 근거를 빠르게 검토할 수 있고, 실패한 이유가 구분된다.

대기열과 동시 통화 확대

앞 단계가 안정된 뒤 예약, 제한된 재시도, 동시 통화 수를 늘립니다. 공급사 한도와 비용 상한을 함께 적용합니다.

완료 기준 · 통화 간 대화가 섞이지 않고, 취소·중복 방지·사용량 집계가 유지된다.

개발 기간은 전화 사업자 가입·번호 검증, 음성 복제 권한, 한국어 인식 품질에 영향을 받습니다. UI 구현량만으로 전체 일정을 정하지 말고 각 단계의 완료 기준을 일정의 기준으로 삼습니다.

테스트와 품질 기준

자연스러운 말투와 정확한 연락처 확보를 함께 평가합니다.

ID테스트 상황기대 결과
T01정상적으로 전체 번호 제공자리별 낭독 후 상대의 확인 발화와 번호를 연결해 저장

T10다른 지시·다른 번호 발신을 요구상대 발언으로 기록하고 서버의 발신 범위를 유지

정확도 지표

  • 번호 정확 일치율: 사람이 확인한 정답과 모든 숫자가 일치하는 비율
  • 잘못된 성공 처리: 불완전·미확인 번호를 완료로 분류한 건수
  • 재확인 증거율: 성공 건 중 재확인 발화가 연결된 비율
  • 업무 완료율: 전체 작업 중 원하는 연락처를 확보한 비율

통화 품질 지표

  • 응답 지연: 상대 발화 종료부터 봇의 첫 음성까지
  • 말 끊기 지연: 상대 발화 시작부터 봇 재생 중단까지
  • 침묵·반복: 긴 무응답이나 같은 질문 반복 횟수
  • 완료 비용: 연락처 확보 한 건에 사용한 총비용

첫 검증에서는 통화 전체를 검토하고, 오류가 STT·LLM·TTS·전화 연결 중 어디서 발생했는지 표시합니다. 정답을 아는 테스트 시나리오와 실제 업무 통화를 구분하며, 응답 지연은 평균뿐 아니라 느린 통화를 나타내는 상위 구간도 확인합니다.

목표값은 직접 측정한 뒤 정합니다.특정 응답 속도나 번호 확보율을 사전에 보장하지 않습니다. 숫자 오류와 잘못된 성공 처리를 먼저 줄이고, 같은 테스트 조건에서 모델·템플릿·음성 설정을 비교합니다.
11

운영·비용·확장

실제 운영에서는 통화 품질, 재시도, 사용량을 함께 관리합니다.

비용은 여러 서비스 사용량의 합입니다.

총비용 = 전화 연결·번호 비용 + 음성 인식 비용
　　　　+ LLM 비용 + 음성 합성 비용 + 서버·저장 비용연락처 1건 확보 비용 = 실패·부재·재시도를 포함한 해당 기간의 총비용 ÷ 성공적으로 확보한 고유 연락처 수

공급사마다 통화 시간, 음성 길이, 문자 수, 토큰 등 과금 단위가 다릅니다. 현재 계약과 요금표를 기준으로 계산하고, 무료 구간이나 특정 분당 단가를 전제로 사업성을 판단하지 않습니다. 성공 건이 없으면 확보 비용을 0으로 표시하지 않고 산정 불가로 표시합니다.

발신 정책

  • 건물별 중복 문의와 이미 확보한 번호 확인
  • 업무 목적에 맞는 발신 시간 설정
  • 통화 시간과 재시도 횟수 상한
  • 거절·잘못된 번호의 재발신 제외
  • 소개 번호는 별도 후보로 저장
  • 전체 작업을 멈추는 중단 기능

데이터 운영

  • AI 대리 통화와 기록 방식 안내
  • 업무에 필요한 연락처와 근거만 보관
  • 대화록·녹음의 보관 기간 설정
  • 사용자별 목소리와 결과 접근 권한
  • API 키는 서버에서 관리
  • 작업·목소리·기록 삭제 기능

실서비스 전에는 선택한 통신사의 자동발신 조건과 실제 통화 기록·개인정보 처리 방식에 맞는 요건을 확인합니다. 이 문서는 법률 판단을 대신하지 않으며, 대화록과 녹음을 남기는 방식에 따라 운영 설계가 달라질 수 있습니다.

확장은 가장 큰 실패 원인부터 해결합니다.

부재가 많으면 발신 시간과 재시도 정책을, 숫자 오류가 많으면 음성 인식과 재확인 문구를, 통화 중 끊김이 많으면 응답 지연과 말 끊기 처리를 개선합니다. 한 번에 여러 요소를 바꾸지 말고 템플릿·모델·목소리 버전을 기록해 비교합니다.

후속 기능으로 ARS 키패드 입력이 필요하다면 전화 공급사의 별도 제어 지원을 확인합니다. Twilio 양방향 Media Streams의 DTMF 지원은 수신 방향으로 제한되므로, 현재 음성 스트림만으로 모든 ARS 조작이 된다고 가정하면 안 됩니다.[3]

용어와 공식 참고 자료

설계 제안과 공급사가 제공하는 기능을 구분해 확인합니다.

STT · Speech to Text상대방 음성을 텍스트로 바꾸는 음성 인식 기능.
TTS · Text to Speech텍스트를 음성으로 만드는 기능. 등록한 목소리를 지정할 수 있습니다.
LLM문맥을 이해하고 답변과 실행 의도를 생성하는 언어 모델.
Streaming전체 결과를 기다리지 않고 음성·텍스트 조각을 순차적으로 처리하는 방식.
WebSocket통화 중 음성과 이벤트를 지속적으로 주고받는 연결 방식.
Webhook연결·종료 같은 사건이 발생했을 때 공급사가 서버에 보내는 알림.
VAD / Barge-in발화 시작·종료 감지 / 상대의 끼어들기에 맞춰 봇 발화를 중단하는 처리.
SIP / PSTN전화 연결을 제어하는 통신 규약 / 일반 전화망.
Idempotency · 멱등성같은 요청이 반복돼도 중복 발신 등 추가 효과가 발생하지 않는 성질.
DTMF전화 키패드의 숫자 입력 신호. ARS 메뉴 선택 등에 사용됩니다.
